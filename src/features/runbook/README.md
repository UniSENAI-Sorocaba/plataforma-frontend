## SSR Specifics
- **Static vs. Dynamic Routes**: Files under `src/app` that contain a `page.tsx` are treated as routes. Use `export const dynamic = 'force-dynamic'` to enforce SSR for a route when needed.
- **Data Fetching**: Prefer `fetch` with `next: { revalidate: 0 }` for server‑only data. Avoid using browser‑only globals (`window`, `document`) in server components.
- **Hydration Errors**: If you see a mismatch between server‑rendered HTML and client hydration, ensure that any client‑only code is wrapped in a `use client` directive or placed inside a client component.
- **Environment Variables**: Server‑only env vars must be prefixed with `NEXT_PUBLIC_` if they need to be exposed to the client.

## Debugging Tips
1. **Inspect Server Logs** – Run `npm run dev` and watch the terminal for SSR errors.
2. **Check Network Requests** – Use browser dev tools to verify that API calls are made from the server (shown as “fetch” in the Network tab with `initiator: fetch`).
3. **Use `next-telemetry`** – The project includes telemetry hooks that can be enabled to trace rendering phases.
4. **Common Pitfalls**:
   - Importing a client‑only library in a server component.
   - Missing `await` on async data fetches, causing the component to render before data is ready.
   - Using relative paths that resolve differently on server vs. client.

## Deployment
- Build the app with `npm run build`.
- Deploy the `.next` output to a Node.js compatible hosting platform (e.g., Vercel, Render, Cloud Run).
- Ensure the runtime environment has the same Node version and environment variables as the local setup.
